# OpenHut gotchas

Things that bit the v1 build; each is handled in the code it names. The code carries no comments, so the reasons behind
the installer, agentd and the e2e run live here. `openhut-server.md` covers the app and `hermes.md` covers Hermes.

## Postgres and the gateway

- **node-postgres runs `{text, values: []}` over the simple protocol**, which executes several statements (`commit; delete …` escapes a read-only transaction). Only `values.length > 0` or `queryMode: "extended"` forces one statement. The gateway also wraps every query in `declare … cursor` + `fetch 1001`, which caps memory and allows only SELECT/VALUES (`packages/runtime/src/server/integrations/postgres/postgres.ts`).
- **A read-only transaction doesn't contain a superuser**: `COPY … TO PROGRAM` and server-file functions still work. Refuse superuser and `pg_execute_server_program` / `pg_*_server_files` roles.
- **pg connection strings let `?host=` override the URL's host** and `?sslrootcert=` read local files. Parse into explicit fields; allow only `sslmode`.
- **`net.BlockList` matches IPv4-mapped IPv6** (`::ffff:127.0.0.1`) against IPv4 rules; `new URL` rewrites that to `::ffff:7f00:1`.
- **A `lookup` hook never runs for IP-literal URLs.** Checking addresses in undici's `connect.lookup` alone let
  `http://127.0.0.1/` through; `guardedFetch` also checks literal hostnames in its connector (`platform/network.ts`).
- **`OPENHUT_AGENT_GATEWAY` (Mac, microsandbox microVMs) drops the subnet check.** Agents get that URL (e.g. `http://host.microsandbox.internal:8081`) instead of `http://10.200.<net>.1:8081`, their calls arrive through microsandbox's host-side proxy from loopback, so the gateway listens on `127.0.0.1` only and `byToken` accepts a valid token from `127.0.0.1`/`::1` instead of the agent's `/24`. The trade-off: any local process holding an agent's token can call the gateway as that agent. The token is secret and stays inside that agent's own VM, so the HMAC token is the only thing tying a call to an agent in this mode.
- **Hermes's Telegram cold start needs `deleteWebhook` to succeed** (PTB's polling bootstrap calls it, and Hermes drops the adapter on a non-network error), so the broker passes it and refuses only `logOut`, `close` and `setWebhook`. Telegram method names are case-insensitive; the list is compared lowercased.
- **The Claude plugin's relay refuses a plain-HTTP upstream unless it's loopback.** The gateway is `http://10.200.<net>.1:8081`, so our patch lets the configured `relay_upstream` be HTTP; `ANTHROPIC_BASE_URL` keeps upstream's rule.
- **Broker paths are checked after URL normalisation**, and that same normalised path is what's forwarded: `/v1/../complete` is checked as `/complete`, and a percent-encoded `/v1/%6Dessages` matches nothing and is refused.
- **The MCP SDK's refused-code error has an empty message** (`invalid_grant` with no description); the sign-in wraps it.

## Local dev

- OpenHut installs only on Linux (Debian, Ubuntu or Alpine; x86_64 or arm64): gVisor, the iptables firewall and systemd need a Linux kernel, and a native macOS port would drop the sandbox. On a Mac, run `install.sh` inside a Linux VM (OrbStack, Lima, UTM). The installer checks the OS before root so a Mac user isn't asked for sudo first.
- macOS caps Unix socket paths at 104 bytes; a long `AGENTD_SOCK` is cut short and fails with `EADDRINUSE`.
- Two worktrees can't run `npm run dev` at once: the gateway (8081, `config.ts`) and the fake Hermes and Slack (18642, `dev.ts`) are fixed, and `PORT` only moves 8787 (`seed-ui.ts` reads `PORT` too). To check the UI from a second worktree, change those locally, run with `PORT`, and revert before committing. Don't point Vite at another worktree's app: it may be on a different API and the pages fail to parse. Stop your own processes by PID (`lsof -tiTCP:<port>`), never `pkill -f agentd.ts`: every worktree's dev runs the same command line, so it kills theirs too.
- Stop your own dev server by PID (`lsof -nP -iTCP -sTCP:LISTEN`), never `pkill -f scripts/dev.ts`: that also matches other worktrees' servers, and killing only `dev.ts` leaves its app child holding the port.
- `config.port` is 8787 unless `PORT` is set; when an e2e run holds 8787, start the app with `PORT=8799`.
- A second local instance needs more than `PORT`: the gateway port (8081, `platform/config.ts`) and the fake Hermes port (18642, `scripts/dev.ts`) are fixed, so the app dies with `EADDRINUSE` when another worktree is running. Start it from a small script that sets `config.gatewayPort` before importing `app.ts`, with its own fake Hermes on another port and `OPENHUT_AGENT_API` pointing at it. A fresh worktree may also lack `node_modules/@openhut` until `npm install` relinks it.
- `scripts/seed-ui.ts` hardcodes `127.0.0.1:8787`, so on another `PORT` seed from a copy with the port swapped. In the dashboard, "New agent" creates the agent on click (no form), so clicking it for a screenshot adds one.
- The button and dropdown rules (which variant for which action) are in `DESIGN.md` at the repo root and in the `variant`/`size` props of `components/ui/` since 2026-11-16. Screens style with Tailwind utilities and those components; `index.css` holds only the tokens (`@theme`), base element rules and the few scoped blocks utilities can't express (creature SVG parts, chat markdown `.msg-t`; the auth night scene is `features/auth/auth-scene.css`). A new look is a new variant, not a global class. `test/ui-conventions.test.ts` fails on a raw `<button>`, `<input>`, `<select>`, `<textarea>` or `<dialog>` in `features/` or `app/`.
- Tailwind runs without Preflight (`index.css` imports only its theme and utilities), so browser defaults stay: `<p>` keeps its 1em margins and buttons their UA padding unless a class resets them. `text-sm`/`text-xs` carry line-height 1.5; where a parent sets another line-height, use `text-[14px]`, which inherits it. tailwind-merge drops a `leading-*` that comes before a font-size class, so write the size first.
- Base UI skips the backdrop of a dialog opened inside another dialog unless it has `forceRender` (`ui/alert-dialog.tsx` sets it, so nested confirms still dim what's behind). Base UI also rounds popup positions to whole pixels, so a `sideOffset` can't land on a half pixel; the invite popover uses `-mt-[.5px]` (a translate blurs its border).
- Dialogs, sheets and popups are all Base UI and portal to `<body>` with `z-50`, so a select or combobox opened inside a dialog stacks above it (the old native `<dialog>` top-layer workaround is gone). A toast (`z-20`) now sits under an open dialog. `Dialog` focuses what the native `<dialog>` did: the first focusable element or scrolling box (`firstFocusable` in `ui/dialog.tsx`), so a React `autoFocus` inside a dialog is overridden only when it isn't first.
- Dev never calls slack.com: `OPENHUT_SLACK_API` points at a fake Slack in `scripts/dev.ts` (workspace Acme, bot @gus, public, private, shared and group-DM channels). Any `xoxb-…`/`xapp-…` of the right shape connects.

## The installer (`install/`)

- `install.sh` is what `curl -fsSL https://openhut.dev | sh` runs. Outside a container and with no `/opt/openhut`, it only starts the `openhut` container and runs itself inside it (`../decisions/openhut-installs-in-one-container.md`); `/.dockerenv` is how it knows it's inside. There it adds what's missing (Docker, gVisor, Node 22.18+), then OpenHut and the Claude CLI that the seat plugin drives. Every download is checked against a checksum written into the script; `scripts/release.sh` writes openhut.tgz's. Re-running upgrades in place and keeps `/data` and `/etc/openhut/env`. `RESOLVER` and `OPENHUT_MODEL` (claude|test) are read on the first install only. `OPENHUT_CLIENT_KEY_SHA256` (the hex SHA-256 of the key the app enrolls) is required on the first install, kept in `/etc/openhut/env` (0600), and only its first 8 hex characters are printed; without it the installer stops before downloading anything. It ends with `tailscale serve --bg --https=443 http://127.0.0.1:8787` on the host when Tailscale is there, or prints that as the next step.
- `AGENT_IMAGE` overrides the release's pinned Hermes image (`install/agent-image`, by digest) and is remembered in `/etc/openhut/env`. Without it, every upgrade brings that release's pin. `pull-image.sh` pulls the image when it's missing, so a moved pin reaches new agents, then prepares the WhatsApp bridge. A bridge failure leaves WhatsApp off, not OpenHut.
- Package mirrors sometimes hang a connection, so every package and wget call runs under `timeout` and is retried. apk uses `/etc/apk/cache` when the host keeps one.
- A running dockerd re-reads its runtimes on SIGHUP. Agents can't start until it knows `runsc`.
- Each release is extracted to `/opt/openhut.new` and swapped in whole, so nothing from the previous release lingers. Running processes keep the files they have open until they're replaced. Everything under `/opt/openhut` is owned by root and writable only by root, because root runs agentd and the firewall from there.
- The Claude CLI is about 300 MB, so a verified copy is kept in `/var/cache/openhut` for re-installs.
- `uninstall.sh` (owner, 2026-11-13: one command instead of five steps) asks the person to type `uninstall`, then undoes everything `install.sh`, `prepare.sh` and the firewall add, except Docker, gVisor and Node. Each step ignores what's already gone, so it's safe on a half-installed server. Anything new the installer creates has to be added there too. Installs from before it don't have the file; re-running the install command brings it.
- **Update now** (Admin): `scripts/release.sh` writes the build into `install.sh` (`OPENHUT_BUILD`), so the app learns the latest build by fetching the installer from `OPENHUT_URL` (the address the install came from, kept in `/etc/openhut/env`; cached a minute); no version file or registry. The build is a semver (owner, 2026-11-13: no timestamps in Admin): the major.minor of `packages/runtime/package.json` and the number of commits on `main` as the patch, so every merge is a new, higher version with nothing to bump by hand; `release.sh` refuses a shallow clone, where that count would be 1. A higher version is an update; a build that isn't a semver on either side (installs from before this, the e2e's `e2e-N`) is an update whenever it differs; a `dev` build is never offered one. Admin shows only this version; `version` in `/health` is still the package.json one. `POST /api/updates` stores `{from, to, startedAt}` in `install_setting` and asks agentd for `update` with the sha256 of the installer it just read. agentd downloads the installer to a file, runs it only if its sha matches (a release published in between fails with "a newer release came out", so `to` is always what runs, and a cut-off download never executes), and writes its output to `/var/log/openhut/update.log` and its exit code to `update.log.exit`. It must outlive agentd, which the installer restarts, so it runs as the transient unit `openhut-update` (`systemd-run`), or detached without systemd.
- **Update status lives on the server, not in the page** (owner, 2026-11-13: no dialog, it must survive a refresh and the restart, no error noise while it runs). `GET /api/admin` derives it: the build it asked for means done (the record is cleared); any other new build, an installer exit newer than the record (agentd's `health.lastUpdate`), neither the lock nor an exit after 20 s, or 45 min in all, means failed, with `reason` = the installer's last `openhut:` line. The Computers row shows "Couldn't update to X." with that reason and a Try again button. Apps before 0.1.2 can't read `<provider>:<model>` keys, so the runtime sends them the old ids when `openhut-app-version` says so (`forOlderApps` in `platform/responses.ts`).
- **One install at a time, and a failed one changes nothing.** `install.sh` holds `flock` on `/run/openhut-install.lock` (fd 9, closed for `host-start.sh` so the daemons don't keep it), retrying `flock -n` for 10 s (BusyBox's flock has no `-w`): agentd's `health` tests the lock by taking it for a moment, and a single try let an update started while Admin was being polled die at once (e2e UD2, 2026-11-17); agentd reports the lock as `updating` in `health` and refuses a second `update`. Before the swap nothing has changed (a bad download exits there). After it, `/opt/openhut.old` is kept until `/health` is fresh; if that doesn't happen (5 min when the agent image pin is unchanged, else 30) the installer moves the old release back, restarts it and exits 1. Right before the swap it stops the app and copies `/data/app` to `/data/app.before-update`, and a rollback puts that copy back, so a migration the new release ran is undone too. The installer copies `install/recover.sh` to `/etc/openhut/recover.sh`; the firewall unit (`ExecStartPre`) and `host-start.sh` run it first at boot, and when `/opt/openhut.old` is there with the install lock free (a reboot during the health wait), it puts the old release and the data copy back (e2e RC1). The few microseconds between the two `mv`s are still not covered.
- **`set -e` and `$(…)` in the install scripts** (2026-11-18, #167): `X="$(sed … /etc/openhut/env 2>/dev/null)"` ends the script silently when the file is missing, because the assignment takes the command's failing status. A first install never got past the enrolled-key check. Read files that may not exist yet with `|| true` inside the `$(…)`; `2>/dev/null` only hides the message, not the exit.
- The installer waits for a `/health` whose `started` is no earlier than its own start, so the app it replaces can't pass for the new one.
- **In the one-container setup** (found on internal, 2026-11-17): data lives in the container's own filesystem, so `docker rm openhut` deletes every agent, and the `docker:28-dind` it started with is never replaced by Update now or a re-run. The container publishes 8787 on the host's 127.0.0.1 only and the runtime inside binds 0.0.0.0 (`OPENHUT_HOST`), so the host's `tailscale serve` reaches it; from the host's Docker bridge it answers only the enrolled key (2026-11-17, `decisions/app-aggregates-runtimes.md`). Containers made between #121 and #125 published `-p 8787:8787` on every interface. A re-run of the installer finds any container not published on 127.0.0.1 and moves it: `docker stop`, `docker commit openhut openhut:kept` (its filesystem, so `/data` and `/etc/openhut` come along), `docker rm`, and the same `docker run` from `openhut:kept`. The `openhut` volume holds the inner Docker as before.
- **Without systemd** (a container, some VPS images), `host-start.sh` boots in the units' order: firewall, dockerd, agent image, agentd as root, then the app as `openhut`. With no agents yet it pulls the image in the background (log in `pull.log`), so the dashboard is up minutes sooner; `pull-image.sh` holds `/run/openhut-pull.lock` so a second start can't race it. The systemd unit can't do this: systemd kills anything an `ExecStartPre` leaves running. Nothing runs it at boot, and agents have no Docker restart policy, so after a reboot agents stay stopped until it runs. It's safe to run again: it replaces agentd and the app and leaves Docker, the agents and `/data` alone. Docker's pid files survive a container restart (on a real server `/run` is a tmpfs), so it deletes them when dockerd isn't running. As PID 1 of a container it stays up without depending on its children, so a re-install can replace them.
- `supervise.sh LOG CMD…` reruns CMD whenever it exits, like systemd's `Restart=always`. BusyBox `sh` has no `exec -a`, so this script gives the restart loops a name `pkill` can find.
- `prepare.sh` runs before agentd. It makes `/data/app` 0700 and owned by `openhut`, because the database holds `auth_secret` (the unit's `UMask=0077` covers the files). It also writes the agents' `resolv.conf`.
- `whatsapp-bridge.sh` installs the bridge with `--omit=optional --ignore-scripts`. That keeps it pure JS on any libc, leaves out `sharp` (thumbnails) and runs no install scripts as root. The throwaway container it copies the code from is removed even when the copy fails.
- The first agentd start pulls the ~3 GB agent image, so `openhut-agentd.service` has `TimeoutStartSec=infinity`.
- **Docker restart policies start agents before any firewall.** Agents use `--restart no`; the app restarts the ones marked running through agentd, which checks the firewall first.
- **`-v` creates a missing bind source** as an empty root-owned folder; `--mount type=bind` fails instead.
- **A bind mount of a folder that's renamed and deleted shows up empty**, while a single-file bind keeps its file. An upgrade that swaps `/opt/openhut` must restart running agents (the app does it once per new build) or their `plugins/` mount goes empty.

## The firewall (`install/agents-firewall.sh`)

- It runs before dockerd starts and whenever agentd starts. Two chains:
  - `AGENT` (jumped to from DOCKER-USER) is agent traffic leaving the server. It drops Tailscale and allows DNS to the resolver. It allows HTTPS anywhere except private, link-local and CGNAT ranges, and drops everything else.
  - `AGENT-IN` (jumped to from INPUT) is traffic to the server itself. Agents reach only the gateway on 8081, with at most 16 connections per agent `/24`, and nobody else reaches 8081.
- **Rebuilding an iptables chain with `-F` + appends opens it briefly.** `iptables-restore --noflush` with `:AGENT - [0:0]` replaces one chain in one commit and leaves the others alone.
- Each jump must be the first rule of its chain, or a rule above it lets agent traffic skip ours. The script drops any copies and inserts the jump at the top. An `ip rule` at priority 5200 keeps agent networks on the main table, ahead of Tailscale's table 52.
- `--check` compares the chains, both jumps and the ip rule, as iptables prints them, with what was printed right after applying (`/run/openhut/firewall.rules`). One missing or reordered rule therefore counts as off.

## agentd (`packages/runtime/src/agentd`)

- The app sends one JSON line per connection and half-closes its side. agentd answers that line (`allowHalfOpen` keeps its own side open for the reply) and ignores anything after it. Every argument is validated into a typed request (`AgentdRequest`) before Docker sees it.
- `/health` uses a firewall check at most 5 s old, so unauthenticated requests can't make root spawn processes on demand. create, start and restart always check afresh, and concurrent callers share one check in flight.
- The watchdog runs the check every 30 s. When it fails, the watchdog re-applies the firewall, and if that fails too it stops every agent.
- Every docker and firewall call has a 60 s timeout, so one hung call can't hold an agent's queue forever.
- Commands run one at a time per agent, so a start can't land inside another command's stop/start. `restartContainer` is the restart inside a command. `enqueueRestart` is for work outside one (a WhatsApp pairing that ended). Calling it from inside a command would wait on its own queue forever.
- Docker errors other than "already gone" stop a delete, so a container that's still running never loses its row.
- **Container flags reach existing agents through `SPEC`.** Each container carries the label `openhut.spec`; when `apply` finds a different one it removes the container and creates it again (the home folder stays), then starts it if it should run. Bump `SPEC` in `agentd.ts` with any change to the sandbox spec or to the `docker create` flags, which now live in `packages/runtime/src/agentd/sandbox/gvisor.ts` (`createArgs`). `apply` takes the agent's `net` for this.
- Rendered files are owned by root, readable by the agent's group and mounted read-only, so an agent can't change its own limits. Only files whose content changed are rewritten, so a running agent never sees its files truncated for nothing.
- An agent is stale when any rendered file is newer than its start, so a failed restart is retried by the next `apply`. `apply` restarts only when the agent should be running and either its files are stale or `force` is set. `force` means a new release, so the agent remounts the release's plugin and CLI.
- `platforms/` and `.claude/` are mounts of their own. They hold read-only mounts and, being mounts, can't be renamed away and recreated writable.
- **WhatsApp pairing** runs the bridge inside the agent's container. Killing `docker exec` leaves the bridge running inside, so a pairing that ends any way but "linked" restarts the container. A pairing that links restarts it too, so Hermes starts WhatsApp.
  - Only the agent's current pairing restarts it. `stop`, `rm` and `wa-unlink` drop the pairing first; otherwise stopping or deleting an agent mid-pairing brought it back.
  - The bridge's own logs share stdout with its JSON events, so lines that aren't JSON are skipped.
  - The pairing payload is either `2@…` or a `https://wa.me/…` link.

## The e2e run (`packages/e2e`)

- While a run is going, the Docker containers `openhut-host` (holding 127.0.0.1:8787) and `openhut-lan` are its server. Don't run anything inside them and don't edit the tree: the report then says "the tree changed during the run" and the run is no verdict. On 2026-11-13 a run failed only UD2 (build `e2e-3` never healthy) after both happened mid-update; the cause wasn't confirmed. For a local dashboard meanwhile, `PORT=8799 node scripts/dev.ts` works.
- `npm run e2e` runs everything on a Mac with Docker Desktop, in this order:
  1. build `e2e-1` installed with one curl on a bare `docker:dind` server (the only preparation is `apk add curl`), then the `main` phase;
  2. build `e2e-2` with one byte of its `openhut.tgz` changed, installed over it, which must fail and leave `e2e-1` running;
  3. the real `e2e-2` installed over it (the upgrade), then `after-upgrade`;
  4. a server restart, then `after-restart`;
  5. Update now against a release whose app can't start (`update-broken`: rolled back, Admin says failed), then against the real `e2e-3` (`update`);
  6. the report.

  It takes about 25 minutes and needs Node 22.18+ on the Mac and 127.0.0.1:8099 and :8787 free. The script is named `e2e`, not `test`, so turbo's test task never starts it. On a Mac it runs itself under `caffeinate -is`: an idle Mac drops into Maintenance Sleep every ~15 minutes, which freezes Docker's VM while the checks' wall-clock timeouts keep counting (a night run on 2026-11-17 had five false failures that way).
- Releases are served by the site's Worker under `wrangler dev` on :8099, with one release folder as its assets. A mirror left running by an interrupted run (parent gone, on 2026-11-17 from another worktree) keeps :8099, and the next run's readiness `curl` would get an answer from it and install that old release; `mirror()` now fails instead. It listens on 0.0.0.0 so the Docker server reaches it through `host.docker.internal`. `release.sh` deletes and recreates `dist/`, so the mirror is restarted for each release, and the tampered copy gets its own folder, `dist/tampered`.
- The tampered build is `e2e-2`, not the running `e2e-1`, so an install that went through would show up as a changed `BUILD`.
- Named volumes cache Docker images (`openhut-docker`), Alpine packages (`openhut-apkcache`) and the Claude CLI (`openhut-dlcache`). Everything else starts empty. On Docker Desktop, a reused `/var/lib/docker` volume brings back old containers, so `e2e.sh` prunes it to images only.
- Traffic between two Docker networks is dropped by Docker itself, so firewall targets live outside the server: `openhut-lan` listens at an address in each private range and at the metadata address. Every target an agent must not reach is checked from the server too, where it must be open, so "blocked" can only come from the agent firewall.
- `e2e.sh` hashes the tree (`HEAD`, `git diff HEAD` and the untracked files) at the start and again at the end, and the report fails if they differ, so it always describes the code that ran.
- `e2e.ts` isn't part of the release. It's copied onto the server after each install (the upgrade swaps in a clean `/opt/openhut`) and runs there as root, playing the people, the channel and the attacker. `docker cp` keeps the Mac's owner, so the copy is chowned to root.
- Each check is its own `node:test` test, run in order, so one failure doesn't stop the rest. Results go to `results/e2e-<phase>.json`, which `report.ts` turns into `e2e-report.md`, next to the install, tamper and upgrade logs, the server's logs, the container spec, the firewall and the probes' matrices. `main` always writes `state.json` for the later phases: the agent, the OAuth refresh token, the firewall and the PIDs. Refresh tokens rotate, so each later phase saves the new one.
- The upgrade's release pins the same image as `docker.io/<pin>`, so the run can tell agentd took the new release's pin.
- The team DB's TLS files live in `/root`, because the server's `/tmp` is emptied when it restarts and the DB has to come back. `wrong.test` is the DB's address under a name its certificate lacks. The postgres image answers `pg_isready` on its socket during init, before it restarts, so the run waits for a TCP answer.
- The deployed gateway trusts public CAs only, so the test CA passes `sslmode=require` and fails `verify-full`/`verify-ca`. Name checking (K10b) runs `postgres.query` in a scratch process with the test CA trusted. The run has no real Claude subscription, so claude mode's rendered files are a unit test (`hermes-files.test.ts`).
- D6 counts the audit rows it expects as the run goes: every `callTool` and `chat('sql: …')` adds one, by its reply (allowed, `Denied:` or failed).
- The test model echoes a tool result as `TOOL RESULT: <untrusted_tool_result …>preamble\n\n{"result"|"error": …}`. Checks compare the gateway's own text inside it.
- The gateway-limit checks call the gateway straight from the agent's network with its token, because Hermes pauses a server for ~59 s after three refused calls.
- `/health` reads a firewall check at most 5 s old, so the watchdog checks wait for the 503 before acting.
- app.log holds evlog JSON lines, so the run matches events (`build.applied`, `reconcile.started`) rather than text.

## Local dev

- `npm run dev`: `scripts/dev.ts` starts the real agentd with `OPENHUT_SANDBOX=memory` (data `.data/agentd`, socket `.data/agentd.sock`, no root, no Docker) and the server with `OPENHUT_DATA=.data` and `OPENHUT_MODEL=test`, plus Vite for the renderer. The memory sandbox (`packages/runtime/src/agentd/sandbox/memory.ts`) keeps sandboxes in a map and fakes what Hermes would do inside one: it seeds sample skills and memories into the agent's home on first start and plays a WhatsApp pairing (a QR, then linked after 6 s). `dev.ts` also serves the fake Hermes API and Slack on :18642 and puts a fake `tailscale` first on agentd's `PATH` (`.data/agentd/bin`), because agentd calls the host's `tailscale` directly and `ts-down` would otherwise log the Mac out of its real tailnet.
- Open `http://localhost:5173`. `dev.ts` runs the server in remote mode with the dev key `dev` enrolled, and Vite's `/api` proxy sends `Authorization: Bearer dev`. `node scripts/seed-ui.ts` adds sample agents and connections with the same key.
- `scripts/release.sh` runs on macOS (BSD tar) and in CI (GNU tar). Their flags for a root-owned archive differ (`--uid 0 --uname root` vs `--owner=0 --numeric-owner`), so the script picks by `tar --version`; the first CI deploy failed on `--uid`.

## Seat usage (Admin)

- A `claude setup-token` seat has only the `user:inference` scope, so `/api/oauth/usage` refuses it (`user:profile` required) and Claude Code's `get_usage` answers `rate_limits: null`. The plan % comes from the `anthropic-ratelimit-unified-{5h,7d}-utilization` and `-reset` headers of a 1-token Haiku message instead (`count_tokens` carries none). The app sends one per 5 minutes at most, only while someone has Admin open.
- Only windows Claude is tracking come back: often `7d` alone, no `5h`.
- The seat's % also counts anyone else signed in to that Claude account, so per agent we show shares of what agents used, not shares of the seat: agentd sums `estimated_cost_usd` (API list price) from each agent's Hermes `state.db` `sessions`, for sessions active since the weekly window opened. A long session counts in full, including what it spent before the window.
- Admin shows both in one Usage section (the last one), with the explanations in info-icon tooltips (native `title`). It only renders with a set seat in Claude mode, so `npm run dev` (test mode) never shows it. To look at it, serve `packages/desktop/dist/renderer` from a small stub server that answers `/api/me`, `/api/admin` (`seat: { set: true, mode: "claude" }`) and `/api/admin/seat-usage` with sample JSON, and an empty list for every other `/api/` path.

## GitHub bot (`integrations/github/github.ts`)

- The same callback URL is hit twice with one `state`: first with `code` (the app exists; exchange it for the key within the hour, then send the browser to the install page), then with `installation_id`. The sign-in is remembered again between the two, so a restart in between leaves an app on GitHub with no connection; delete it under GitHub's Developer settings.
- The installation is fetched with the app's own JWT before it's saved, so a made-up `installation_id` can't attach someone else's installation.
- A personal-account app can only be installed on that account. For an organization's repositories the app must be created under the organization (the dialog's Organization field), which needs an org owner.
- The bot's permissions are fixed in the manifest (contents, pull requests and issues write; actions and checks read). Pushing changes to `.github/workflows` needs the Workflows permission, added on the app's page on GitHub.
- GitHub connections are saved with `sign_in` false, so there's no Reconnect: a new bot means delete and connect again.
- A grant change restarts the agent (since #95, so `SOUL.md` lists its apps), and the API call returns while Hermes is still starting. The e2e's `chat` and `asAgent` wait for the agent's API first; a check that talks to an agent another way has to do the same.
- To check the dashboard at phone width in Claude in Chrome, don't resize the window (a maximized one ignores it and Chrome won't go below about 600px). Run `npm run dev` (Vite serves the renderer with `/api` proxied to the server), then replace the page with a same-origin `<iframe src="/agents" style="width:390px;height:780px">` (scale it up with `transform` for readable screenshots) and navigate it with `contentWindow.location.href`. The app server itself sends `x-frame-options: DENY`, so only the Vite origin can be framed.
- A live-view bridge (`docker exec -i … bridge.mjs live`) can outlive its viewer: on the internal x86_64 host, closing the exec client's stdin didn't end the process, and two leftovers made the still picture fail intermittently. The bridge exits on its own: agentd pings it every 10 s while its viewer is connected, and the bridge quits after 30 s without a ping or when its stdout breaks. Don't rely on stdin EOF reaching a process through `docker exec`. Repeated one-shot `docker exec` calls were also unreliable there (about half returned nothing, and three in parallel all failed); the live view retries every 3 s while no page is open, so a missed exec only delays it.

## The Mac app (`packages/desktop`)

- **The packaged app runs the server and agentd with `utilityProcess.fork` on Electron's own Node**, not system `node` (Finder gives apps no Homebrew or nvm `PATH`) and not `ELECTRON_RUN_AS_NODE` (the `runAsNode` fuse is off). Dev (`!app.isPackaged`) still spawns `node` on the `.ts` files.
- **Raw `.ts` can't run from `node_modules`** (`@openhut/common`), so `scripts/pack-backend.mjs` bundles both with esbuild. The bundles sit where the sources' `import.meta.url` paths still resolve: agentd at `backend/packages/runtime/src/agentd/agentd.mjs` (`../../../../install/agent-image`, `../../../../bin/claude`), the server at `backend/packages/runtime/src/server/platform/app.mjs` (`config.ts` reads `../../../package.json` for its version). The script also downloads the Linux `claude` CLI the installer pins, for the guest's arch, checks it against the installer's checksum and puts it in `backend/bin/claude` (cached in `dist/`); microsandbox refuses to create a VM when a required mount is missing rather than starting an agent without its CLI. PGlite (wasm) and microsandbox (native `.node`, `msb`, libkrunfw) stay real packages beside them.
- **electron-builder drops `node_modules` from an `extraResources` folder.** The yml copies `dist/backend/node_modules` as its own entry; without it the app has no PGlite or microsandbox.
- **`MSB_PATH` and `MSB_LIBKRUNFW_PATH` are pinned to the copies inside the `.app`**, else a `msb` in `~/.microsandbox` or the npm package wins. VMs started by another `msb` keep running and are still found by name: switching from the dev app to the packaged one kept Ops answering.
- **One entitlements plist for everything** (`allow-jit`, `hypervisor`, `disable-library-validation`), applied as `entitlements` and `entitlementsInherit`, so the helpers, the utility process that loads the `.node`, and `msb` all get it. electron-builder signs every Mach-O under `Contents/` including `msb`, the dylib and the `.node` (no `mac.binaries` needed). `spctl` says "Unnotarized Developer ID" until notarization runs.
- **Cookie encryption stays off**; the app keeps nothing in cookies.
- **The server's root secret (`auth_secret`, which derives the seal key and agent tokens) lives in the Keychain, not the database.** `main.mjs` keeps it in `secret.bin`, encrypted with `safeStorage`, and hands it to the server as `OPENHUT_SECRET`, which `config.ts` deletes from `process.env`. On a database that still holds the row, the server writes it to `secret.handoff` (0600) and deletes the row; main moves it into `secret.bin` and removes the file. A `secret.bin` that won't decrypt stops the boot rather than minting a new key. Without a keyring (Linux `basic_text`) the row stays in the database and `server.log` says so.
- **Dev runs as `OpenHut Dev`** (`app.setName`), so its Keychain item is "OpenHut Dev Safe Storage" and the signed app's is "OpenHut Safe Storage". Sharing one item made the signed app ask for Keychain access, since the item's ACL names whichever binary created it.
- **Dev notifications fail with `UNErrorDomain error 1`**: macOS hasn't allowed the unsigned Electron to post. The signed app asks once. A menu-bar item can sit behind the notch on a full menu bar; `tray.getBounds()` says where it is.
- **The dev and packaged data folders hand out the same agent ports** (`18600 + net`), and VMs outlive the app, so a VM left running by one app makes the other's next agent fail with "Address already in use".
- **Connection sign-ins navigate the main window** (`location.assign` to Google or an MCP server), and the callback to `127.0.0.1`/`localhost` is rewritten to `app://openhut`, so `will-navigate` allows http(s) and only blocks other schemes. `target=_blank` and `window.open` to anything outside `app://openhut` go to the default browser; the claude.ai seat sign-in opens there too.
- **Closing the window keeps the server, agentd and the gateway running** (an empty `window-all-closed` handler); the Dock icon or a second launch reopens it. Cmd-Q sends SIGTERM, the server closes Fastify and PGlite (`app.stopping` in `server.log`), and main waits up to 5 s. VMs are detached from agentd and keep running.
- **Dev and the packaged app can't run at once**: different `userData` (`OpenHut Dev`, `OpenHut`), but both bind the gateway on 8081.
- Logs: `~/Library/Logs/OpenHut` (`OpenHut Dev` in dev), rotated to `*.old.log` past 10 MB at start. Help › Show Logs opens it.
- The MCP bridge is a POSIX sh script (`bin/openhut-mcp`, one `curl --unix-socket` per JSON-RPC line, SSE `data:` lines unwrapped) because the `runAsNode` fuse is off and the assistant's machine may have no Node. The app copies it to `<userData>/bin/openhut-mcp` on every start, and it finds the sockets one folder up (`OPENHUT_HOME` overrides), so the command in Settings › MCP stays the same across updates, AppImage launches (a new `/tmp/.mount_*` each time) and a translocated `.app`. When it can't reach the app it answers a JSON-RPC error for the request's `id` (the last `"id"` in the line).
- **App updates** (`update()` in `main.mjs`): electron-updater fires `update-downloaded` before Squirrel.Mac has fetched and checked the signature, so the app takes "ready" only from Electron's own `autoUpdater` (Squirrel) on a Mac; a refused or failed update shows "Couldn't update" (or "isn't signed by OpenHut") with Download and Check now instead of "Up to date". When an update is verified the app copies its own bundle to `<userData>/previous` (an APFS clone, under a second for 678 MB) before it shows Restart to update. The first start of a new version copies `data/app` to `data/app.before-update` before the runtime migrates it (`booted-version` says which version last started). If the new version can't start, the error dialog offers "Go back to X": it puts the data copy and the previous bundle back, relaunches, and writes `skipped-version` so that version isn't downloaded again. The sidebar's Update pill updates every server that's behind, one at a time, then restarts the app; to a server the app reports the version it has verified and staged, so a release that needs a newer app installs. `OPENHUT_TEST_HOME` (own userData, no relaunch) and `OPENHUT_UPDATE_FEED` (a generic feed) are for `scripts/update-test.mjs`.
- The agents' mount sources (`bin/claude`, `vendor/hermes-plugins`) are copied to `<userData>/assets/<app version>` and passed to agentd as `AGENTD_ASSETS`, for the same reason: microsandbox keeps a bind mount's host path, so a path under `process.resourcesPath` breaks the agent after the next launch. Each sandbox carries an `openhut.mounts` label (a hash of those paths) and `apply` recreates it when it differs; the server applies every agent at boot. The previous version's folder is kept until the one after, so agents still running on it keep their files until they're recreated.
- `build/icon.png` is rendered from `build/icon.svg` (the hut on the 824 px squircle) with an offscreen Electron window; `build/icon.icns` comes from `sips` + `iconutil` of that PNG.

## The Linux app (`packages/desktop`, `dist:linux`)

- **Same code as the Mac app**, branched on `process.platform` in `main.mjs`: userData `~/.config/OpenHut`, logs in `~/.config/OpenHut/logs`, a File menu (Settings, Quit) and About under Help, a normal window frame (no `hiddenInset`; `data-desktop`, the sidebar's traffic-light gap and drag region, is Mac only), and **closing the window quits the app**, since there is no tray to bring it back. Agent VMs are detached and keep running, the same as Cmd-Q on the Mac; the next launch picks them up.
- **No `/dev/kvm` (or no read-write access to it) shows "This computer can't run agents" and quits** before agentd starts. Ubuntu gives the desktop user access through a logind ACL; otherwise it's the `kvm` group.
- **Ubuntu's default umask is 002, and msb refuses a group-writable `~/.microsandbox`** ("catalog ancestor … permits path substitution; refusing to run agents"), which it created itself. `main.mjs` sets umask 022 before anything starts. A `~/.microsandbox` left 0775 by an earlier run needs `chmod 755`.
- **Electron's Linux zip unpacks world-writable (0666/0777)** and fpm keeps those modes, so the deb installed root-owned files anyone could rewrite. `scripts/after-pack.cjs` runs `chmod -R go-w` on Linux, and `dist:linux` runs under umask 022 for what fpm stages after that. `dpkg` keeps an existing directory's mode on reinstall, so check modes on a clean install.
- **The AppImage's `msb` lives in its FUSE mount, which goes away when the app quits**, while the VMs it started keep running and would page-fault into a dead mount. Under `APPIMAGE`, `main.mjs` copies microsandbox to `~/.config/OpenHut/msb-<version>` once and pins `MSB_PATH`/`MSB_LIBKRUNFW_PATH` there. Old versions' copies aren't cleaned up yet.
- The Linux package is `@superradcompany/microsandbox-linux-x64-gnu` (`bin/msb`, `lib/libkrunfw.so.5.6.1`, glibc only); `main.mjs` takes whatever file is in `lib/`. `msb` needs nothing beyond glibc, so the deb has no extra `Depends`.
- **The deb needs `homepage` and a maintainer** (fpm fails without them), and `executableName: openhut`, since the npm name `@openhut/desktop` isn't a valid file name. The deb installs an AppArmor profile for Chromium's sandbox on Ubuntu 24.04; the AppImage has none, so where `kernel.apparmor_restrict_unprivileged_userns=1` (stock Ubuntu 24.04 desktop) it needs `--no-sandbox` or that profile. The AppImage needs `libfuse2` (`libfuse2t64`), or `--appimage-extract-and-run`.
- Auto-update isn't tried on Linux yet: electron-builder writes `latest-linux.yml`, electron-updater replaces an AppImage in place and updates the deb through `DebUpdater` (`pkexec dpkg -i`). With no release on GitHub it logs "No published versions" to `updates.log` and carries on.

- A model id is `<provider>:<model>` and the model part can hold `/` and `:` (OpenRouter). Split on the first `:` only (`splitModelKey`). Rows from before 2026-11-18 held bare ids (`sonnet`, `codex`); `migrate()` rewrites them and `splitModelKey` still reads them, so older move bundles import.
- `npm run dev` needs 8081 free for the gateway; an installed OpenHut holds it. Set `OPENHUT_GATEWAY_PORT=18081`. A long `OPENHUT_DATA` path breaks agentd's Unix socket (`EINVAL`), keep it short.
- A `pkill -f scripts/dev.ts` from a shell whose own command line contains that text kills the shell. Kill by port.
