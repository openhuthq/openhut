# Hermes

Every agent runs on Hermes Agent (Nous Research, MIT). Docs: https://hermes-agent.nousresearch.com/docs

- One agent = one profile = one container (`brain/decisions/one-container-per-agent.md`).
- Profiles don't sandbox: file tools and the shell can read anything the process user can.
- No HTTP API creates profiles or starts gateways. Run `hermes gateway run` in the foreground with `HERMES_HOME` set; `gateway start` needs systemd and `-p <id>` ignores `HERMES_HOME`.
- The gateway multiplexes by default (`gateway.multiplex_profiles`): one process serves every profile, and `gateway.profile_routes` sends a channel, chat or user to a profile. That only keeps profiles organised; they share one process, one OS user and one disk. Hermes SECURITY.md: capability separation needs separate instances, and "the only security boundary against an adversarial LLM is the operating system".
- An agent can read its own `.env` (a plain `cat` isn't flagged). Env scrubbing, the approval regex and output redaction are heuristics, so keep team keys in our gateway.
- Approvals are off (owner, 2026-11-13): every agent renders `approvals.mode: "off"` (quoted, or YAML reads it as false), Hermes's equivalent of `--yolo`, because the container is the boundary and nothing in it is worth a prompt. Before that it was `manual` with the owner and the channel owner as approvers, and `smart` for open channels. Hermes still refuses its hardline list (`rm -rf /`, fork bombs, `mkfs`, `dd` to a disk). What an agent can reach outside the sandbox is still only what the gateway grants it. How approvals work when on: whoever's message triggered a command can always approve it, on top of `approvals.approvers` (which defaults to `"*"`, so set it). Approvals are answered in the chat that raised them.
- A rate limit with a named reset is waited out for up to 600 s per retry (`agent.api_max_retries`, default 3).
- Claude subscription: the official `claude-subscription-directsdk` plugin runs the Claude Code CLI. It accepts `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`, needs `USER` set and a writable `CLAUDE_CONFIG_DIR`, and is experimental. **Neither the plugin nor `claude` ships in the Hermes image** (only a catalog entry pinning hermes-official-plugins `6313fad`); OpenHut vendors the plugin and mounts both read-only (`plugins/` is `$HERMES_HOME/plugins`). `sonnet`/`opus`/`haiku` aliases need Claude Code ≥ 2.1.293.
- Tool Search is on by default and hides MCP tools behind `tool_search`/`tool_call`. OpenHut agents set `tools.tool_search.enabled: "off"`, because our gateway already discloses tools progressively.
- The API server channel needs `API_SERVER_KEY` of at least 16 characters, or it silently doesn't start ("No messaging platforms enabled").
- Under gVisor, Hermes sees bind-mounted folders as a cross-VM filesystem and switches SQLite to `journal_mode=DELETE` (slower, still safe).
- Hermes v0.23.1 (image 3.2 GB, arm64 + amd64) runs as `--entrypoint /opt/hermes/bin/hermes gateway run` under runsc, uid 10000, with a read-only root; pass `--init`.
- Hermes runs its own Slack (Socket Mode) and WhatsApp (QR bridge) gateways. Two profiles can't share a Slack token.
- `config.yaml` is writable by the agent's own tools unless mounted read-only. Hermes also imports `hooks/*/handler.py` at startup; mount `hooks/` read-only and set `PYTHONNOUSERSITE=1`.
- gVisor can't use Docker's embedded DNS on user networks; mount a `resolv.conf`.
- MCP: `mcp_servers.<name>` with `url` + `headers`; tool filters via `tools.include`/`exclude`. Config changes need a restart.
- Channel approvals (pairing) live in `platforms/pairing/`, or in legacy `pairing/` as soon as that has any file, so lock both read-only or an agent can approve outsiders for itself.
- Under gVisor with `--init`, Hermes is always PID 2, so after `docker stop` + `start` its own stale `gateway.pid` (or, failing that, `gateway_state.json`) looks live and it exits ("A gateway is already running (PID 2)") until the status goes stale (~90 s). agentd deletes `gateway.pid`, `gateway.lock` and `gateway_state.json` before every start; `HERMES_GATEWAY_LOCK_DIR` points at the per-start `/tmp`.
- Hermes pauses an MCP server for ~59 s after three refused calls in a row ("rejected the last 3 calls … Paused"). Gateway denials count, so an agent probing what it may do locks itself out for a minute.
- Slack runs in Socket Mode: `SLACK_BOT_TOKEN` + `SLACK_APP_TOKEN` (`connections:write`), `SLACK_ALLOWED_USERS` (member IDs) or `SLACK_ALLOW_ALL_USERS=true`. OpenHut sets allow-all plus `SLACK_ALLOWED_CHANNELS` (`brain/decisions/openhut-slack-channels.md`). Strangers' messages are dropped silently, never answered with a pairing code. Its lock needs a writable `HERMES_GATEWAY_LOCK_DIR` (a read-only `$HOME` makes connect fail with EROFS).
- Slack gates (read in the v0.23.1 source by a reviewer, 2026-11-15, not run live): the user check comes first, so someone outside `SLACK_ALLOWED_USERS` is dropped even in an allowed channel. `SLACK_ALLOWED_CHANNELS` then drops other channels; empty means every channel. 1:1 DMs skip the channel list, group DMs don't. There is no allow-by-channel-membership. Hermes re-reads `.env` on each turn, after authorising that message. The bot token sits in the agent's own `.env`, so every Slack scope in the manifest is one a tricked agent holds (`channels:join` would let it join and read any public channel).
- WhatsApp never shows a QR from the gateway: it refuses to start the bridge until `platforms/whatsapp/session/creds.json` exists, and doesn't retry. Pair with `node <bridge>/bridge.js --pair-only --pair-json --session …` inside the container: JSON lines `qr` (raw payload, rotates ~20 s), then `connected`; restart the agent after. Killing the `docker exec` client doesn't stop it.
- The image ships the bridge's code but no `node_modules` and no npm, so Hermes would `npm install` at runtime. OpenHut prepares it per image on the host (`install/whatsapp-bridge.sh`, with the `node_modules/.hermes-pkg-hash` stamp = first 16 hex of sha256(package.json)) and mounts it read-only at `$HERMES_HOME/scripts/whatsapp-bridge`, which Hermes uses when its install tree isn't writable.
- `WHATSAPP_ALLOWED_USERS` takes digits (`+` stripped); `*` is everyone and empty is nobody. Approvers are compared as the bridge reports senders: `<digits>@s.whatsapp.net`.
- Telegram is Hermes's own gateway too (long polling, so nothing reaches into the server): `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_USERS` (numeric user IDs, never usernames) or `TELEGRAM_ALLOW_ALL_USERS=true`. `python-telegram-bot` is baked into the image (the `messaging` extra), so nothing installs at runtime. An allowlist already makes strangers' DMs silent; we still set `telegram.unauthorized_dm_behavior: ignore` and `require_mention: true`. Approvers are the numeric ID. A second poller on the same token gets a 409 conflict, so one bot per agent.
- API server chat (`/v1/chat/completions`) is stateless: send the whole conversation. `stream: true` sends OpenAI chunks plus `event: hermes.tool.progress` lines when a tool starts, and `: keepalive` comments every 10 s. Each tool call sends two progress events with the same `toolCallId`: `status: running` with a `label`, then `status: completed` without one (there is no failed status). The `label` is the tool's argument preview, not a display name: for `execute_code` it is the whole script (seen at 1,664 chars), and for the gateway's `call_tool` it is the app tool's name. The chat pairs them by id (`features/threads/steps.ts`). A bare `model` is ignored (the profile's model answers). `/v1/models` is the readiness check.

- Toolsets (owner, 2026-11-13): `browser`, `delegation` and `cronjob` stay off. `code_execution` is on by default and each agent's page has a switch for it (`agent.code_execution` → `agent.disabled_toolsets`). The browser was switched on and off again the same day (owner: maybe later). Before it comes back: local Chromium has never been run under gVisor with the 1 GB limit, and a browser reads far more untrusted text, which gVisor does nothing about (a tricked agent can still send out what it holds).
- Skill files: `skills/<name>/SKILL.md` or `skills/<category>/<name>/SKILL.md`, with `name:` and `description:` front matter. Hermes copies its ~44 bundled skills into every agent's `skills/` at start and lists them in `skills/.bundled_manifest` (`name:hash` lines). A bundled skill someone edited no longer matches its hash, so Hermes keeps the edit and stops updating that skill.
- Skills (owner, 2026-11-13): `skills/` is the agent's own writable folder in its home, so Hermes saves skills it learns. It was an empty read-only mount before. A planted skill survives restarts, like a planted memory.
- Heartbeats (checked on v0.23.1, 2026-11-14): Hermes has two. `/heartbeat every <interval> <prompt>` is one recurring prompt inside one conversation (60 s minimum, state in `state.db` under `heartbeat:<session_id>`, cleared on reset, no HTTP route), so the dashboard can't set or show it. Scheduled jobs are the durable one: the gateway ticks every 60 s in every agent even with the `cronjob` toolset off, and the API server takes `GET/POST /api/jobs`, `PATCH/DELETE /api/jobs/:id` and `/pause`, `/resume`, `/run` with `API_SERVER_KEY` (create takes `name`, `schedule`, `prompt` ≤ 5000 chars, `deliver`, `skills`, `repeat`). Each run is a fresh session; Hermes itself tells it to answer `[SILENT]` when nothing is new. Runs land in `cron/executions.db` (`status`, `delivery_outcome`: `delivered`/`suppressed`/`failed`) and `cron/output/<job_id>/<time>.md`; the API has no route for past runs. Without a `*_HOME_CHANNEL` Hermes answers a person's first message with a "📭 No home channel is set… type /hermes sethome" notice (`gateway/run_turn_prepare.py`, no switch turns it off), so OpenHut sets `SLACK_HOME_CHANNEL` to the first picked channel and `TELEGRAM_HOME_CHANNEL` to the owner's chat (owner, 2026-11-16: "do not send this message"). WhatsApp still has none: its chat ID format is unchecked. A bare `deliver: slack` now lands in the home channel.
- Sending (checked on the internal instance, 2026-11-15): `send_message` is deliberately not an agent tool ("the agent must not fire cross-platform messages on its own"). `hermes send --to <platform>[:chat[:thread]] --file -` in the container posts with the gateway's own credentials and no model call, and `hermes send --list --json` lists targets as `{ platforms: { telegram: [{ id, name, type, thread_id }] } }`. It prints an "install out of sync (pnpm…)" warning on stderr in our image; ignore it. Automations post through it (`brain/decisions/openhut-automations.md`).
