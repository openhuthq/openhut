# OpenHut v1: verification plan

## The goal being verified

One command installs OpenHut on a server. OpenHut deploys many Hermes agents. Each agent:
- runs in its own isolated container;
- has its own instructions and channel;
- reaches team data only through one MCP gateway, which holds the keys and checks per-agent grants on every call.

Everything is managed from the OpenHut desktop app (Mac and Linux), or from your own AI assistant over the control MCP. The app is a window over runtimes: one on this computer and one on each computer you add (`brain/decisions/app-aggregates-runtimes.md`). Each runtime has one implicit owner: on the app's own computer whoever can open its 0600 socket, on an added computer whoever holds the key the app enrolled. There are no people, passwords or sign-in.

The test story comes from scoping. A **Dev** agent may query the team's Orders database; a **Sales** agent may not. Neither can reach:
- the other agent;
- the server;
- the database directly;
- the customer's LAN;
- the cloud metadata address.

Refused connections: ones that log in as a superuser, as a member of one, or as a role that can run server programs or touch server files. The gateway connects to the address it checked, but checks TLS against the DSN's name. `sslmode` keeps libpq's meanings (`require`, `verify-ca`, `verify-full`), and it's the only connection-string option allowed. `verify-*` trusts public CAs only; a private CA can't be configured in v1 | |

## Install and the e2e run

How the installer works, and how `npm run e2e` runs it on Docker Desktop (a bare server, the install, adding it again with a new key, a tampered upgrade, the real upgrade, a restart, the caches and what lands in `packages/e2e/results/`), is in `brain/openhut-gotchas.md`. The run has five phases, each a run of `e2e.ts` with its results in `e2e-<phase>.json`: `main` (after the install), `after-upgrade`, `after-restart`, `update-broken` (Update now with a release whose app can't start: the installer puts the previous build back) and `update` (Update now from Admin's API). The e2e runs the remote runtime only: gVisor, the firewall and the enrolled key; the desktop app is verified by hand (see "Not verified here").

## Checks

Each check is one `node:test` test in `packages/e2e/src/e2e.ts`, which names what it proves and what it expects; a run's `packages/e2e/results/e2e-report.md` lists them all with the actual values. Two worth naming:
- **T1** is a unit-level check run on the server: it loads `events.ts` in local mode in a node process and checks the usage data it would send has no email, login or username. The desktop app's own telemetry is not exercised end to end.
- **F8** asks agentd for its fence report and requires exactly the six checks above, all passing on gVisor. F4 and H5 probe the same ground from a real agent: every blocked target must time out from the agent (dropped, not reset) while the server reaches it, including stand-in listeners at 10.99.0.10:443 and 169.254.169.254:443 and one the run holds open on the server itself.

## Accepted risks in v1

- **Whoever holds the app's key owns that runtime.** The app keeps it in the system keychain; the runtime keeps only its SHA-256. The key works from anywhere that reaches the runtime: loopback, `tailscale serve`, and inside the curl install's container the server's own Docker bridge.
- **An agent reads its own `.env`.** That includes its channel key and its own Slack tokens; Hermes needs them to hold its own Slack connection. The Claude seat, the ChatGPT token and Telegram bot tokens are not there: the agent holds only its own gateway token, which the gateway swaps for the real key.
- **In the desktop app another local program can take 127.0.0.1:8081 while the app is closed.** Agent VMs keep running after quit, so their model and tool calls (carrying only the agent's own token) would go to whatever holds the port. When the app starts again and can't bind 8081 it stops every agent and exits rather than run beside it (`brain/decisions/desktop-app.md`).
- **In the desktop app any process running as the same user can open the server's 0600 socket** and act as the owner.
- **WhatsApp linking runs the bridge's pairing mode inside the agent's container** for up to 5 minutes. A phone that scans the code links its number to that agent; only people who can edit the agent see the code.
- **An agent can write its own cron jobs** (`cron/jobs.json`, though the cronjob toolset is off). They run as that agent with its own grants: persistence, not escalation. Scheduling is a later feature, and its UI will own this file.
- **No per-agent disk quota.** One agent can fill `/data`. Quotas (XFS project quota or a loop image) come later.
- **An agent writes its own skills** (`skills/` in its home). Instructions planted by a message can persist there, as they can in its memories. They run with that agent's grants only.
- **Code execution is on by default**, with a switch per agent. It runs in the same sandbox as the shell, which every agent already has.
- **The browser is off by default**, with a switch per agent. It is agent-browser (Vercel Labs, pinned and checksummed by the installer) driving the Chromium in the Hermes image, inside the agent's own container and on its own network, so it reaches what the shell reaches and nothing else. The agent can read its own browser's cookies, so a login given to an agent is the agent's to use or leak. A page can carry text written to steer the agent. Chromium's own sandbox is off; gVisor is the sandbox. With Browser on the container's memory limit is 4 GB instead of 1 GB. People who can edit the agent see a still picture on its page, a live view in a new tab, and can take over; while a person holds it, agent-browser's action policy denies the agent's actions. Checks R1 to R6.
- **Private database CAs.** `verify-ca`/`verify-full` work with publicly trusted certificates only; a private CA can't be configured in v1 (use `require`, which encrypts without checking).
- **Root on the server can read everything.** `auth_secret` sits next to the sealed DSNs in `/data/app`, which is mode 0700.

## Pass criteria

1. `npm run e2e` exits 0 on a fresh run: every check in all five phases passes, and the report says the tree matches what the run tested. `npx turbo run build typecheck test` passes.
2. The result files exist and match the report.
3. Three reviewer agents return **zero comments**. Each is briefed only with this plan, the code, the results and read-only access to the live server:
   - **Senior software engineer**: is the code correct and minimal, and does it do what this plan claims?
   - **Security / SRE**: does the evidence prove each isolation and permission claim, and is anything exploitable that the checks miss?
   - **QA / verification**: does every check test what it says, could any pass falsely, and is anything in the goal unverified without being listed above?

   Every comment is either fixed (and the run repeated) or answered with evidence, until all three say zero.
4. The user signs off on mock parity (see above).
